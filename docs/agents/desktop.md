# Desktop shell (Electron)

## Scope, layout and the empty preload (`desktop/`, `electron-builder.yml`)
- The desktop app is the same web product in a thin Electron shell. No desktop-only UI, no IPC for product data: the page loads a loopback origin and uses the same HTTP/SSE API, cookies and downloads as the browser build. Everything desktop-specific lives under `desktop/`; `app/`, `components/`, `hooks/` and `lib/` stay shared.
- `desktop/main/` is the shell (window, session cookie, navigation policy, backend supervision, quit state machine), `desktop/preload/` the preload, `desktop/server/` the backend entry and its Next listener, `desktop/shared/` the protocol both sides parse, `desktop/packaging/` the build and smoke scripts. `electron-builder.yml` (repo root) is the packaging config.
- `desktop/preload/index.ts` is deliberately empty: no `contextBridge`, no `ipcRenderer`, no globals. The file exists only because `BrowserWindow`'s `preload` points at a compiled module. There is no `ipcMain` handler in the shell at all — adding one is a product decision, not a shell detail.
- The app version comes from the root `package.json`: `build-desktop.mjs` writes it into `dist/desktop/app/package.json`, so the DMG and the bundle are named after pi-web, not after the shell. One exception: macOS takes `CFBundleShortVersionString` and `CFBundleVersion` as 1-3 period-separated integers, and electron-builder copies `version` into both verbatim, so `pack()` passes the version's numeric base (`0.15.0` of a `0.15.0-imp-0.1.0` fork release) as `--config.mac.bundleShortVersion` and `--config.buildVersion`. The bundle's plist therefore carries the base while `package.json`, the baked `NEXT_PUBLIC_APP_VERSION` and the tag carry the whole fork version — do not "fix" the plist back to the tag.
- The shell's own version lives in `desktop/version.json` (`0.1.0`) and is display data only: `next.config.ts` bakes it, with the build's commit id, into a desktop build (`NEXT_PUBLIC_DESKTOP_VERSION`), so the product's version line reads `<pi-web version>-desktop-<desktop version>-<commit>`. A web build bakes an empty string there and reads `<pi-web version>-imp-<commit>` instead (`lib/build-version.ts`, see sessions.md). A desktop build without that file fails rather than shipping a mislabelled version line, and changing it never renames an artifact.
- The commit id comes from `PI_WEB_COMMIT` when it is set (CI, and `docker build --build-arg PI_WEB_COMMIT=$(git rev-parse --short HEAD)`: `.dockerignore` keeps `.git` out of the image), otherwise from `git rev-parse --short HEAD` in the build's working tree, otherwise `unknown`.
- `lib/desktop-env.ts` and `lib/desktop-auth.ts` are the only `lib/` files the desktop side owns: the environment names, the stripping/redaction helpers and `isDesktopMode()` / the desktop session check.

## Process phases and the message protocol (`desktop/main/backend-supervisor.ts`, `desktop/shared/backend-protocol.ts`)
- Phases are `idle → starting → ready → stopping → stopped | failed`. Every transition is logged with a stable event name (`backend.ready`, `backend.stopped_signal`, …), which is what `smoke-desktop.mjs` asserts against.
- Messages are single JSON objects over the child's stdio: `session` (main → backend secret), `shutdown` (`timeoutMs` clamped to 30 s–120 s, default 60 s), `ready` (`origin`, which must be loopback origin text), `fatal` (a bounded message), `stopped` (`code`). Each has an exact-keys validator in `backend-protocol.ts`; an unknown or malformed message fails the phase machine instead of being ignored.
- `stopped` is an acknowledgement, not proof of exit. The supervisor waits for the handshake *and* the process exit, in that order, each with its own deadline, before it hard-kills; a backend that acknowledges but hangs is still killed after the grace period.
- The backend runs in `electron.utilityProcess.fork()` of `Resources/backend/desktop/server/index.js` when packaged, `dist/desktop/server/index.js` when not. It uses Electron's bundled Node, so a packaged app needs no system Node.js. Its environment is the resolved GUI environment plus `PI_WEB_DESKTOP=1` and `PI_WEB_DESKTOP_LOG_DIR`; the session secret is added per start and handed over through the logger's secret list for redaction.
- A failed start shows a native error box with the log directory and exits `1`. A backend that dies later surfaces the failure in the window and in the menu's `Retry Backend` / `Open Logs`; there is no automatic restart loop, because a crash loop is worse than one visible error.

## Development mode is not a second dev server (`desktop/main/development-server.ts`)
- An unpackaged run is development mode: `classifyDevelopmentProbe()` reads `http://127.0.0.1:30141` as `attached` (a healthy Pi Web), `absent` (start one) or `occupied` (something else).
- Only `absent` spawns, and it spawns exactly `npm run dev` with `shell: false` and the app path as cwd — never a second `next dev` on another port (both would contend for `.next/dev/lock`) and never `next dev --webpack`.
- `occupied` is a hard failure. The shell never kills a process it did not start, and it never silently reuses a stranger's port.
- A dev surface is loaded without the production cookie (`loadBackend(url, null)`): the dev server has no desktop session, and the browser-build auth rules apply unchanged. On quit the shell stops only a dev server it spawned; an attached one keeps running.
- There is intentionally no `dev:desktop` npm script; the launch path is opening the compiled shell, and `build:desktop` is the only desktop build entry point.

## Window, cookie and navigation policy (`desktop/main/window-manager.ts`, `desktop/main/navigation.ts`, `proxy.ts`)
- `secureWindowOptions()` is the only way a window is built, for the main window and for `window.open` alike: `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`, `allowRunningInsecureContent: false`. Webviews are rejected outright.
- Production order is fixed: set the cookie, await it, probe the complete first page, then `loadURL`. Loading before the cookie exists would show an unauthenticated shell (a flash of the password screen or a 401 page).
- The cookie `__pi-web-session` is host-only (no `domain`), `path: "/"`, `HttpOnly`, `Secure`, `SameSite=Strict`, session-only (no expiry), and removed during cleanup. The renderer cannot read it; the secret behind it is 32 random bytes (64 hex) generated per launch in the main process and handed to the backend over the utilityProcess IPC channel in one `session` message (`child.postMessage(createSessionHandoff(secret))` right after `ready`, read from `process.parentPort`). It never travels over argv, an environment variable, a file, a URL, a log line or a preload global, and the backend registers it with the logger redactor so a printed copy is masked.
- Navigation: an in-origin navigation stays; `window.open` is always denied and remapped; a credential-free `http(s)` URL goes to the system browser exactly once — including a loopback URL on another port, so an agent's link to a local page (a preview server, another Pi Web instance) behaves as it does in the browser build; anything else is dropped. The window itself never leaves the backend origin. Permissions default to deny, with a small fixed set allowed for the backend origin only.
- `proxy.ts` takes the desktop branch before the Web password path: a valid desktop session passes, a mutation additionally requires `Origin` to equal the desktop origin exactly, and without the cookie the normal `PI_WEB_PASSWORD` rules apply — fail-closed when no password is set.
- Host/origin checks in the backend are not relaxed by desktop mode. Of the shell's variables, only `PI_WEB_DESKTOP=1` and `PI_WEB_DESKTOP_LOG_DIR` are actually put into the child environment; `PI_WEB_DESKTOP_SESSION` exists as a name the shell still strips (a fallback the backend accepts for tests and direct starts) and is not how a packaged launch receives the secret. Those names plus `PI_WEB_PASSWORD` are stripped from terminal shells, agent command environments and MCP stdio environments and redacted from logs. Only those names are filtered: a generic `*_TOKEN` sweep would break the provider credentials the pi SDK reads.
- The renderer sandbox is not an OS sandbox for pi extensions. Extensions run in the backend with the privileges pi normally gives them; do not describe the shell as sandboxing them.

## Notifications and the notification centre (`lib/browser-notifications.ts`)
- Completion and extension prompts notify through the web Notifications API, and the client prefers a service worker's `showNotification` when one is registered. Electron never presents that call (electron#13041): the click never reaches the OS, so every notification vanished without an error. Our Electron user agent is therefore detected (`isElectronRuntime()`) and the window constructor is used, which is the path a browser takes when no worker exists.
- Delivery also needs a signed bundle (see packaging above): `UNNotification` is the macOS backend from Electron 42 on, and it drops notifications from an unsigned app. Both halves are required — the renderer change alone still shows nothing on macOS, and the signature alone cannot help a service-worker call.
- The shell grants the `notifications` permission for the backend origin only; the request still arrives from the page, so a denial is logged as `permission.denied permission="notifications"`.

## Backend entry, listener and shutdown (`desktop/server/`)
- `index.ts` refuses to start without its handoff: the session arrives either in the `session` message from the parent port (`HANDOFF_TIMEOUT_MS` 30 s — the packaged path) or in `PI_WEB_DESKTOP_SESSION` (tests and direct starts), is validated as 64 lowercase hex, is installed into the auth context, and is **deleted from the environment** when it came from there, before Next or the pi SDK loads. A session received by message extends the redactor, so the value is masked in console and log output. The entry then asserts the standalone root, `chdir`s into the server directory (relative requires and public assets depend on it), and reports `ready` with the real listener origin.
- `next-server.ts` listens on `127.0.0.1:0` and takes the port the OS assigns: no probe-then-close race. It requires `Host` to equal that exact `127.0.0.1:<port>` authority and, when present, the exact `Origin`, and it guards upgrades the same way. It boots Next through the private `next/dist/server/lib/router-server.js` `initialize()` API — a Next major upgrade can break that import, which is why the smoke test is part of the packaging gate rather than an optional extra.
- SIGTERM, SIGINT, `uncaughtException` and `unhandledRejection` all enter the same shutdown, so a crash still cleans up sessions and PTYs.
- `lifecycle.ts` is one idempotent promise: refuse new requests → stop accepting → `shutdownAgentSessions()` → `releaseAllTerminals()` → close upgraded sockets → close Next and HTTP → `destroyConnections()` → send `stopped` → 50 ms flush → `exit(0)`. Each step has its own deadline (`max(1 s, budget / 4)`); a step that fails or times out is logged and the rest still run. That is what keeps one hung session from leaving node-pty children, MCP servers or the listener behind.
- The cleanup functions are loaded lazily (`import("../../lib/rpc-manager")`, `import("../../lib/terminal-manager")`): the shell must not load the SDK before the handoff, and a session-registry failure must not prevent terminal release. Tests inject fakes, so no test loads the SDK or opens a port.

## Packaging (`desktop/packaging/build-desktop.mjs`, `next.config.ts`, `electron-builder.yml`)
- `npm run build:desktop` runs: Next standalone into an isolated `distDir` (`PI_WEB_DESKTOP_BUILD=1`, `PI_WEB_DESKTOP_DIST_DIR=dist/desktop/next`) → copy `.next/static` and `public` into the standalone tree → top up production `node_modules` from the lockfile → compile the shell with `tsc` (a `--noEmit` type gate first, then the emit) → assemble `dist/desktop/app` and `dist/desktop/backend` → a frozen layout check → `electron-builder --mac --arm64` with `CSC_IDENTITY_AUTO_DISCOVERY=false`.
- Flags: `--skip-next` (reuse the built distDir), `--dir` (unpacked `.app` only), `--skip-pack`. They exist so a packaging fix does not re-run a ten-minute Next build.
- `next.config.ts` switches to `output: "standalone"` and the alternate `distDir` only when `PI_WEB_DESKTOP_BUILD` / `PI_WEB_DESKTOP_DIST_DIR` are set. The web build is byte-for-byte the same as before, and `dist/desktop/next` keeps the dev server's `.next` untouched (a desktop build must never be able to break `npm run dev`).
- The backend is an `extraResources` copy at `Resources/backend`, never inside the asar: it needs real filesystem paths and its own `node_modules`. The smoke test asserts that no `app.asar.unpacked/backend` appears.
- `app.asar` is **not** shell-only in the current build: the shell (`main`, `preload`, `shared`) is ~160 KB, but electron-builder still packs the root project's production `node_modules` into the asar (measured 298 MB, with native packages unpacked to `app.asar.unpacked/node_modules`: `@earendil-works`, `@img`, `@next`, `node-pty`, `quickjs-wasi`). That tree is a duplicate of the backend's dependencies and the shell does not require it at runtime, yet it inflates every artifact. Treat it as a known size limitation and packaging trap: `files: ["**/*"]` with `directories.app: dist/desktop/app` does not narrow the dependency set, and trimming it means an explicit `files`/`asarUnpack` allow-list that must then be re-verified by the smoke test.
- Standalone output nests at `standalone/<distDir>`, so the assembled tree moves the server files to `.next` and rewrites `distDir` in `required-server-files.json`. Backend `lib/` modules are copied next to their shims so `desktop/server` and the Next routes resolve the **same** module instance — two copies would mean two session registries and two terminal registries.
- `node-pty` is the native dependency that matters: the darwin-arm64 prebuild (`prebuilds/darwin-arm64/pty.node`) and an executable `spawn-helper` must survive into `Resources/backend/next-standalone/node_modules`. Next tracing can drop them, so the build's layout check and the smoke test verify them instead of trusting the trace.
- `electron-builder.yml` pins `electronVersion`, sets `identity: null` and `hardenedRuntime: false` (no Developer ID), macOS minimum 12.0, and `publish: null`. Artifacts: `release/mac-arm64/Pi Web.app` and `release/Pi Web-<version>-arm64.dmg`, where `<version>` is caught by `artifactName` in `electron-builder.yml` from the whole `package.json` version (a fork release gives `Pi Web-0.15.0-imp-0.1.0-arm64.dmg`, indistinguishable from upstream's `Pi Web-0.15.0-arm64.dmg` only if that macro is dropped); both `dist/` and `release/` are git-ignored.
- The app icon is `mac.icon → resources/icon.png`, a 1024×1024 PNG that carries its own rounded-square background: macOS does not mask an app icon, so a transparent-cornered mark would show as a floating shape. electron-builder derives the bundle's `.icns` from it, which is why the source must stay square and at least 1024 px. `resources/icon.svg` is the same mark as a vector source for regenerating it; the web build's `public/icons/{icon-192,icon-512,apple-touch-icon}.png` are that same mark at their head-declared sizes, so a rebrand replaces `resources/icon.png` plus those three and nothing else (the login page, the empty-session hero, `lib/favicon-badge.ts` and the PWA manifest all read them by path). The design archive it arrived in is not committed (`*.zip` is git-ignored).
- `afterPack` (`desktop/packaging/after-pack.mjs`) then applies an **ad-hoc** signature so the bundle's identifier is `dev.piweb.desktop` instead of the `Electron` one it inherited. This is not cosmetic: the notification centre identifies an app by its signature, and since Electron 42 `UNNotification` refuses to deliver from a bundle macOS cannot identify, so notifications silently never appeared. A real identity (`CSC_LINK` / `CSC_NAME`) skips the step because electron-builder signed the bundle already.
- The packaged backend ships no `npm`/`npx` of its own. Plugin and skill installs therefore use the `npm` / `npx` found on the user's `PATH` (`nodeCliInvocation()` falls back to the bare command name when no bundled CLI script is found). Do not document the desktop app as installable-without-Node for those features.

## Quit, failure and the absence of a tray (`desktop/main/quit-coordinator.ts`, `desktop/main/app-controller.ts`)
- Closing the last window quits; there is no tray, no background agent and no "keep running in the background" option. A running agent does not silently outlive the window.
- The window close is prevented until the quit coordinator approves it (`handleLastWindowClose`), and an interactive quit reads `/api/agent/running` first (`desktop/main/activity.ts`): with a run, a subagent or a non-idle answer it shows one modal plain-text confirmation whose Cancel is the default button, so a stray Cmd-W cannot kill a run mid-turn. Anything unexpected is reported as `unknown` and treated conservatively, and the read is bounded (3.5 s) so a wedged backend cannot block quitting.
- `SIGINT`/`SIGTERM` and `before-quit` paths are non-interactive: they log `quit.noninteractive` and shut down without a dialog, which is what the smoke test's SIGTERM check relies on.
- The quit coordinator is one promise reused by `before-quit`, SIGINT/SIGTERM, window close and failure paths: request backend shutdown with the budget, wait for the handshake and exit, then remove the cookie and destroy windows. A second signal, or a backend that outlives its stop grace, falls through to the hard kill.
- Production cleanup order is backend → cookie → window, so no window is left pointing at a dead origin with a valid cookie.
- `reportFailure()` keeps the shell alive with a diagnosable window instead of exiting: the logs stay reachable and `Retry Backend` restarts the backend without relaunching the app.

## GUI environment recovery (`desktop/main/environment.ts`)
- A Finder or Dock launch does not inherit the user's shell `PATH`. `resolveGuiEnvironment()` runs the login shell once (`zsh -lic`, bounded by `GUI_ENV_PROBE_TIMEOUT_MS` and `GUI_ENV_PROBE_MAX_BYTES`), parses a marked block of the output, and merges only the environment into the backend's env.
- The probe environment is stripped of desktop variables, the probe runs no project command, and its output is never shown as agent content. A failed probe falls back to the system environment with `fallbackPath()`, and the reason is logged; a missing `PATH` must degrade to "some tools not found", never to "the app does not start".
- `PATH` is the one variable the merge does **not** let the main process win. A launchd-launched app starts with `/usr/bin:/bin:/usr/sbin:/sbin`, so "main process wins" would silently discard Homebrew, pnpm and every per-user bin directory; `mergeSearchPath()` instead returns an ordered union — the login shell's entries first, then any main-process entry it did not report. Without that, a bundled tool such as `qmd` (the pi-memory extension's `memory_search`) was reported as not installed in the app while the same machine's browser build found it. Every other variable keeps the rule "login fills gaps, an explicitly set main-process value wins".

## Tests and the gates (`desktop/**/__tests__`, `desktop/packaging/smoke-desktop.mjs`)
- The desktop suite is `node:test` over injected fakes — no Electron binary, no SDK, no listening port: protocol validators, phase transitions and timeouts, cookie-before-load ordering, navigation and external-link decisions, dev classification, handoff/config refusals, host/origin guards, ordered shutdown with timeouts, and redaction.
- It is run with `node --import ./desktop/main/__tests__/ts-resolve.mjs --test --test-timeout=20000 desktop/shared/__tests__/*.test.mjs desktop/main/__tests__/*.test.mjs desktop/server/__tests__/*.test.mjs`. `npm test` globs `app/`, `components/`, `hooks/`, `lib/` and `public/` only, so desktop tests are **not** part of it — run them explicitly when touching `desktop/`.
- `npm run smoke:desktop` (`[--app <path>] [--timeout <ms>]`, default `release/mac-arm64/Pi Web.app`, 90 s) is the packaging acceptance check: frozen layout paths, backend outside the asar, the node-pty prebuild and its executable `spawn-helper`, the shared `~/.pi/agent` directory, the app launching, `backend.ready` with an origin in `main.log`, the loopback page answering, the API refusing an unauthenticated request, a clean quit on SIGTERM, the backend's `[desktop] shutting down` line, the `backend.stopped_signal` handshake, no failed shutdown step, and no orphaned backend process.
- Two things the smoke test deliberately does not prove, and neither should a doc claim them: an authenticated `200` (the secret exists only in the main process) and the rendered DOM. The window's contents, extension UI and terminal behaviour still need a manual pass on the real app.
- The desktop package exists for macOS arm64 only. Windows and Linux are unbuilt and untested; nothing in the shell or the packaging scripts claims otherwise.
