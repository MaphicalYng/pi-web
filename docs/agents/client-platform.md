# Mobile and browser behavior

## Mobile software keyboard (`hooks/useViewportHeight.ts`)
- While an editor has focus and the visual viewport is more than `KEYBOARD_MIN_HEIGHT_PX` (60px) shorter than `innerHeight / scale`, the hook writes `visualViewport.height` to `--app-viewport-height`; smaller shrinks are Safari toolbars. Always compare against that zoom-corrected height, or iOS auto-zoom and pinch zoom leave the composer behind the keyboard.
- WebKit settles the shrunken height only after the keyboard animation, often without another `resize` (bugs.webkit.org 265578), and an IME candidate bar resizes the keyboard with no viewport event at all. So every trigger, composition/input/keyup events on a focused editor included, starts one non-restarting chain of re-reads (`SETTLE_DELAYS_MS`). Reading once per event keeps the full-screen height, and `scrollTo(0, 0)` then fights the page scrolling to the caret: a jittering composer.
- The same check sets `<html data-keyboard-open>`. Under `(max-width: 640px), (pointer: coarse) and (max-height: 500px)` (phone landscape included; tablets keep their controls) CSS hides `.chat-input-controls`, `.extension-status-shelf` and a fresh composer's project bar (`.new-session-context`, its own rule: tapping it would close the keyboard anyway) and drops the bottom safe-area padding the keyboard covers. `MobilePwaLayout.test.mjs` asserts each targeted class exists on its component, so a rename cannot leave a rule silently dead.
- `.chat-input-controls` stays while its model picker is open (`:not(:has(...))`, a rule of its own): the picker's panel lives in that row and its filter is the field the keyboard opened for, so hiding the row hid the picker and blurred the filter (#1271). See [models.md](models.md#model-selector-and-the-mobile-keyboard).
- Anything fixed to the bottom of a phone screen sits inside `--app-viewport-height`, never at `bottom: 0`: iOS keeps the layout viewport, and with it `bottom: 0`, under the keyboard. The drawer and the right panel use `top: 0` with that height; the sidebar's bottom sheet (`.sidebar-sheet-layer` in `app/sidebar-menu.css`) is a layer of that height with the sheet at its bottom, and drops its safe-area padding under `html[data-keyboard-open]`.
- The composer's queued steer/follow-up rows scroll in their own box, `min(180px, 25%)` of `--app-viewport-height` (plain `dvh` misses a keyboard that shrinks only the visual viewport), with the count and Recall above it (#1428). The composer sits outside the scrolling transcript, so an unbounded list pushed the input and its buttons below the screen with no way to scroll them back. The composer's wrapper, fieldset and inner column are flex columns that may shrink (`min-height: 0`), so in a window too short even for that cap the queue box gives way down to its header and one row (`minHeight: 72`) before the input and buttons leave the screen; the 200px draft cap is unchanged.

## Composer paste recovery (`handlePaste` in `components/ChatInput.tsx`)

- Dictation tools (CosyVoice) write the transcript to the clipboard, post Cmd+V and restore the old clipboard soon after. When that write lands during the `paste` event, Chrome checks the clipboard again before inserting and drops its own insertion: `beforeinput insertFromPaste` with `data: null`, no `input` (#1513). The native paste stays in charge; `handlePaste` remembers the event's text and selection, `handleInput` clears that, and a `setTimeout(0)` inserts the text with `replaceTextareaRange()` only when no `input` came and the event was not prevented. Never take over every plain-text paste: Chrome's `execCommand("insertText")` takes seconds on a few thousand lines (4,000 lines: 13.6 s against 28 ms native).

## Terminal shell (`terminalShell()` in `lib/terminal-manager.ts`)
- A new terminal on Windows starts PowerShell as pi's `powershell` tool finds it, through the SDK's `getPowerShellConfig()`: PowerShell 7 (`pwsh.exe`), then Windows PowerShell (`powershell.exe`), and only without either `ComSpec` / `cmd.exe` (#1394). That is Windows Terminal's default too. The lookup is `where`, so a Store install's `WindowsApps` alias is what gets spawned; node-pty spawns it as it would the bare name. The tool's `-NoProfile -Command` arguments are not reused: the terminal is interactive. Elsewhere it is `$SHELL -l` (`/bin/sh` without `SHELL`).
- There is no shell setting and no `shell` field on `POST /api/terminal`: one default, and anyone who wants cmd or Git Bash types `cmd` / `bash` in the tab. A refreshed page's tabs reconnect to their own PTY (`createTerminal()` returns the record for a known id), so they keep the shell they started with; only new tabs pick it again.

## Terminal extra keys (`components/TerminalExtraKeys.tsx`, `lib/terminal-extra-keys.ts`)
- A touch device held in portrait gets Termux's two key rows under the terminal (`ESC / - HOME ↑ END PGUP`, `TAB CTRL ALT ← ↓ → PGDN`). Portrait comes from `screen.orientation` (then `window.orientation`), never from the viewport: the soft keyboard makes the viewport wider than tall, and the keys must stay while it is open. Left and right are Noto Sans Mono's `↓` and `↑` rotated 90deg: its latin subset has `↑`/`↓` but no `←`/`→`, which would fall back to a heavier system font.
- The keys are the panel's last grid row, so xterm's `ResizeObserver` refits above them instead of being covered. Buttons call `preventDefault()` on pointer and mouse down so the hidden xterm textarea keeps focus and the keyboard stays up.
- Keys go through `terminal.input(sequence, true)`, the same `onData` path (and the same connected / disableStdin checks) as typing. Arrows and Home/End follow xterm's application cursor mode; CTRL and ALT are one-shot and also modify the next character typed on the soft keyboard (`applyTerminalModifiers` in `onData`).

## Terminal theme (`lib/terminal-theme.ts`, `hooks/useTerminalTheme.ts`)
- The terminal header's sun/moon button switches the terminal alone between dark (the default) and light, apart from the app theme. The choice is per browser in `localStorage` (`pi-web:terminal-theme`), shared by every open terminal and synced across tabs by the `storage` event.
- A switch sets `terminal.options.theme` on the live xterm, never recreating it, so the shell and its SSE stream stay. The panel's chrome reads `--terminal-*` variables that `.terminal-panel[data-terminal-theme="light"]` overrides; `--terminal-bg` must match each xterm palette's `background`.

## Terminal font size (`terminalFontSize()` in `hooks/useChatAppearance.ts`)
- The terminal has no size setting of its own (#1277): it follows General's chat font size the way code blocks do, the same step from its own 13px at the 14px default (`terminalFontSize()`: chat − 1, so 11–23px). A slider move sets `terminal.options.fontSize` on the live xterm and refits through the panel's `fitAndResize`; the refit's `onResize` sends the new cols/rows to the PTY, the same path as a window resize.

## Sidebar breakpoint (`components/AppShell.tsx`)
- The mobile drawer starts closed on entering the mobile breakpoint. Desktop open state is remembered separately, seeded from the URL's initial `sidebarCollapsed` value and updated only by explicit desktop toggles. Returning to desktop restores that preference; mobile drawer toggles, backdrop clicks and toolbar actions must not replace it.

## Global shortcuts (`hooks/useKeyboardShortcuts.ts`)
- Ctrl+Alt+N starts a new session in the active project's cwd; `isNewSessionShortcut()` is the one place that decides. The letter (`event.key`) matches, so the shortcut follows the layout. The physical key (`code === "KeyN"`) matches only when `key === "Dead"`: macOS treats Option as a character-input modifier, so `Option+N` is a dead key (`˜`) in the U.S., ABC and British layouts and Chrome reports `key === "Dead"` with `ctrlKey`/`altKey` intact, which a letter-only match never fired on (#1335). Never match `code` alone: Windows reports AltGr as Ctrl+Alt, and where AltGr+N types a character (Polish `ń`) that keydown is the user's text, which `preventDefault()` would swallow.
- Esc stops the running agent unless the event is already `defaultPrevented` (a nearer Settings, menu or viewer closed on it) or the focus is a `TEXTAREA`/`INPUT`, which ChatInput owns. See [mcp-settings.md](mcp-settings.md) for the Escape stacking that depends on this.
- Ctrl+` toggles the bottom terminal dock. `isTerminalDockShortcut()` matches the physical key (`code === "Backquote"`) rather than the character, because what a keyboard types on the key left of `1` is the layout's own (German `´`, Czech `'`) while the key sits in the same place; an event without `code` (hand-built in a test) falls back to the character instead. Alt, Meta and Shift are refused: Cmd+` is macOS's window switcher, AltGr arrives as Ctrl+Alt on Windows, and Ctrl+Shift+` types a character of its own. It is checked before the new-session shortcut and works inside a focused terminal too — nothing else there consumes Ctrl+`.

## Bottom terminal dock (`components/TerminalDock.tsx`, `lib/terminal-dock.ts`)
- Ctrl+` opens a terminal under the composer and above the extension shelf, so the shelf keeps the bottom of the column: `ChatWindow` renders it from its `terminalDock` slot, which `AppShell` fills. It is a shell of its own, apart from the right panel's terminal tabs (`components/terminal-tab-state.ts`), started in the directory the page shows (`selectedSession.cwd`, then `newSessionCwd`, then `activeCwd`) and left there until it is terminated.
- The dock is a child of `.chat-extension-dock`, with the extension status shelf: the live overlays (background tasks, rpiv-todos) anchor to the wrapper's top edge (`bottom: calc(100% + 6px)`), so they float above the terminal instead of over it. Keep it inside that wrapper — anchored to the shelf alone they cover the shell the reader is typing in.
- Hiding is not closing: the dock stays mounted with `display: none`, so the PTY, its scrollback and its SSE stream survive a collapse and Ctrl+` brings it straight back. A reload reattaches through `pi-web:terminal-dock` in `sessionStorage` (`createTerminal()` returns the record for a known id), which also restores whether it was open.
- Its height is the reader's: `useResizablePanel` with `axis: "vertical"`, `growthDirection: "up"` (the top edge is the handle) and `pi-web:terminal-dock-height` in `localStorage`. `lib/terminal-dock.ts` holds the shares — 35% of the chat column by default, at least 120px, at most 85% so the composer stays reachable; the column is measured through `getAvailableHeight()` on `AppShell`'s chat area, with a fallback before it reports a height.
- `TerminalPanel` renders the dock's two header buttons only when the dock passes them: the chevron hides it (`onHide`), the X ends the shell (`onTerminate` sets `closing: "close"`, the panel's `onClosed` then clears the tab). Restart reuses the right panel's `closing: "restart"` and starts a new tab in the same cwd.
- A typed `exit` closes the dock by itself, and only it: `lib/terminal-shell-input.ts` tracks the line being typed (`trackShellInput()` over xterm's `onData`) so `TerminalPanel` can tell a shell the reader ended from one that ended any other way, and it calls `onExit` only for `exit`/`exit 1`/`logout` (`isExitCommand()`). `AppShell`'s `handleTerminalDockExited` then drops the tab, so the next Ctrl+` starts a fresh shell instead of reattaching to a dead one. Every other ending — Ctrl+D at the prompt, a crash, a server-side kill, a dropped connection — keeps the pane and its "进程已退出，退出码 N" notice, where the reader can still read the output and close it with the X. Keys that move or rewrite the line (arrows, Tab completion, Ctrl+C/Esc) discard it: an untracked line never counts as `exit`, so a mis-detected close cannot happen, at the cost of a completion-typed `exi<Tab>` not closing the dock.

## Opening the browser at startup (`bin/pi-web.js`, `bin/browser-opener.js`)
- The launcher opens the browser once `GET /` has answered and its body arrived (`openWhenServing()`, `waitForFirstPage()`), not on Next.js's "Ready" line. Next prints "Ready" before it loads its request handlers, and the first request then also waits out the pi SDK import `instrumentation-node.ts` starts (#964): about 0.55 s on macOS, but #964 measured the import alone at 5.6 s on Windows, and a launch whose first navigation outlasts the service worker's 8 s timeout opens on `offline.html` (#1358). Any status counts and redirects are followed: with `PI_WEB_PASSWORD` the proxy answers `/` with a redirect to `/login` while the SDK import is still running, so stopping at that redirect left the browser's navigation waiting for the rest of it. A wildcard bind is asked on loopback (`getOpenUrl()`), port 0 opens at once, and after 30 s the browser opens anyway. The run record still goes out on "Ready": status, stop and open list a record only once its URL answers.

## Completion sound
- `hooks/useAudio.ts` stores the toggle in `localStorage` as `pi-sound-enabled` and reuses one `AudioContext`.
- Autoplay policy requires unlocking sound from a user gesture: `ChatInput` calls the unlock hook from interactive controls, and `ChatWindow` plays the tone from `onAgentEnd`.
- A running context keeps an audio output stream open even when silent (an Android `AudioMix` wake lock, #1157), so it runs only around a chime or an unlock: `AUDIO_IDLE_SUSPEND_MS` after the last `resume()` settled it is suspended, unless a newer one is still outstanding, and turning sound off suspends at once. An unlock resumes a suspended context from the send's gesture (about 1 s of output stream per send), which lets later chimes resume it without one (Chrome and Firefox check the page's sticky activation; WebKit lifts its gesture restriction for good once that context started in a gesture). It is never closed: a new context made outside a gesture would stay silent on Safari.
- Firefox for Android leaves the `resume()` of a suspended context pending while the phone is locked, so a run's chime never played there (device report on #1178). `ChatWindow` therefore holds the context running while its session's `agentRunning` is true (`holdAudio()`, released when the run ends or the window unmounts): the output stream stays open during a run, not between runs. Chimes for sessions in other workspaces come from the sidebar's running poll, which stops while the page is hidden, so they never needed a hold. A chime whose `resume()` took longer than `AUDIO_STALE_CHIME_MS` (3 s) is dropped instead of playing when the user is back, including one requested before the page's first gesture.
- A stopped run is not a finished one (pi 1.1's `agent_settled.aborted`, which pi's own status reporting reads as idle, not done): `onAgentEnd({ aborted })` plays no tone and AppShell shows no browser notification, and the wrapper sends no "Task finished" push (`lastRunAborted`). The wrapper's `prompt_done` carries `aborted: true` for it, since the client finishes a prompt it sent on `prompt_done`, not `agent_settled`. A new prompt clears it as the wrapper hands it to pi, not when pi accepts it: pi accepts a command that awaited a run of its own only after that run settled, and that run's Stop must still count.
- One completion, one alert (#1515). A hidden or unfocused page announces the run itself from its stream (`handleAgentEnd()`, through the service worker registration), and the server pushes the same completion to every subscription regardless of pages (`notifySessionComplete()`), a few hundred ms later. Both use the tag `pi-session-complete:<id>` with `renotify: true` (#701, so a later task re-alerts over an old notification still in the tray), so the push replaced the page's notification and alerted twice. Each notification carries `data.shownAt`; the service worker shows every push (iOS revokes a subscription whose push shows nothing, #728) but with `renotify: false` when a same-tag notification is under `RECENT_NOTIFICATION_MS` (10 s) old. A push later than that still alerts twice.
- Only a run owes the "Task finished" push: the wrapper marks one at `agent_start` (`agentRunNeedsCompletion`), never when pi accepts a prompt. pi accepts an extension command it ran (and input an extension swallowed) as `handled` with no run, and reports a command that calls `pi.sendUserMessage()` handled before that run starts, so marking at acceptance pushed for every `command:` button and twice for a command that starts a run (#1345).
- A main session's run that ends while one of its subagents can still report back announces nothing: no push, no chime, no browser notification, no unread dot (#1434). Each background report starts a run in the parent (`notifyParent()`, `triggerTurn`), and the run after the last one is the end of the task. The one test is `hasUnsettledSubagentRun()` (`lib/subagent-runtime.ts`), the lease's `subagentsActive`: the wrapper skips the push, marks that run's `agent_settled` and `prompt_done` `subagentsActive: true` (`onAgentEnd({ subagentsActive })` then plays and shows nothing), and `/api/agent/running` lists those sessions as `subagentsActiveSessionIds`, which the sidebar counts with the running ones, so a session completes when it leaves both, even if no poll saw its last run. A parent notification stops counting once the turn it triggers has started (pi sets the run active before its first await, and `sendCustomMessage()` resolves only after that turn settled), or else the turn's own end would still find it pending; one whose result the parent already collected with `get_subagent_result` does not count, since it is dropped without a turn. A report that cannot be delivered starts no run, so nothing is announced for it. A grandchild still running under a subagent that already reported does not hold the main session back: the main session never hears from it. A run leaves the run map in `finally` (`dropSubagentRun()`), and the queue reports `queued` before an item joins it, so a status write that throws (a full disk) cannot leave a run there that holds its parent's completion until a restart. Known limit: when an extension's async `agent_settled` handler outlasts the 200 ms parent poll, pi only queues the report's turn (`_deferredSettledActions`), the parent is not running yet, the pending entry goes when `sendCustomMessage()` returns, and that family is announced twice, as before this rule.
